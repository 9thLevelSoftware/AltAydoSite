<objective>
Implement a MongoDB-backed rate limiter for authentication endpoints, replacing the in-memory rate limiter for auth routes while keeping the in-memory limiter for general API routes.

Purpose: SEC-10 requires persistent, distributed rate limiting on auth endpoints. The current in-memory rate limiter (Map-based) is lost on server restart and per-instance in multi-process deployments, making brute force attacks trivial to circumvent.

Output: `rate-limit-store.ts` with MongoDB-backed atomic rate checking; auth endpoints integrated; TTL index for auto-cleanup.
</objective>

**rate-limit-store.ts:** Create new module following the pattern from 10-RESEARCH.md:

1. Define `RateLimitDoc` interface: `{ key: string, count: number, windowStart: Date, expiresAt: Date }`
2. Collection name: `rateLimits`
3. Export `checkRateLimit(key: string, maxRequests: number, windowMs: number)` function:
   - Get db via `connectToDatabase()` from `@/lib/mongodb` (use the same pattern as other storage modules)
   - Use `findOneAndUpdate` with `$inc: { count: 1 }` and `$setOnInsert: { windowStart, expiresAt }` with `upsert: true, returnDocument: 'after'`
   - Query filter: `{ key, windowStart: { $gte: new Date(now - windowMs) } }` to find entries within the current window
   - Return `{ allowed: boolean, remaining: number, resetAt: Date }`
   - Atomic operation prevents race conditions (Pitfall 2 from research)

4. Export helper `getRateLimitKey(prefix: string, request: Request)` that extracts client IP:
   - Fallback chain: `request.headers.get('x-forwarded-for')?.split(',')[0]?.trim()` -> `'unknown'`
   - Format: `"${prefix}:${ip}"` (e.g., `"auth:login:192.168.1.1"`)
   - Note: Next.js `Request` object doesn't have `.ip` property directly -- use headers (Pitfall 4)

5. Export constants for default thresholds:
   ```typescript
   export const AUTH_RATE_LIMIT = {
     maxRequests: parseInt(process.env.RATE_LIMIT_AUTH_MAX || '5'),
     windowMs: parseInt(process.env.RATE_LIMIT_AUTH_WINDOW_MS || '300000'), // 5 minutes
   };
   ```

**mongo-indexes.ts:** Add index creation for the `rateLimits` collection in the existing index setup:
- `{ key: 1 }` - unique lookup index
- `{ expiresAt: 1 }` with `expireAfterSeconds: 0` - TTL index for auto-cleanup

Follow the existing fire-and-forget pattern with `.catch(() => {})` that Phase 8 established.

  <action>
For each auth endpoint, add rate limiting at the top of the POST handler (before any other logic):

1. Import `checkRateLimit`, `getRateLimitKey`, `AUTH_RATE_LIMIT` from `@/lib/rate-limit-store`
2. Extract rate limit key: `const rateLimitKey = getRateLimitKey('auth:login', request)` (use appropriate prefix per endpoint: `auth:login`, `auth:signup`, `auth:forgot-password`, `auth:reset-password`)
3. Check rate limit:
   ```typescript
   const rateLimit = await checkRateLimit(rateLimitKey, AUTH_RATE_LIMIT.maxRequests, AUTH_RATE_LIMIT.windowMs);
   if (!rateLimit.allowed) {
     return NextResponse.json(
       { error: 'Too many requests. Please try again later.' },
       {
         status: 429,
         headers: {
           'Retry-After': String(Math.ceil((rateLimit.resetAt.getTime() - Date.now()) / 1000)),
           'X-RateLimit-Remaining': '0',
         },
       }
     );
   }
   ```
4. Add rate limit headers to successful responses too:
   ```typescript
   response.headers.set('X-RateLimit-Remaining', String(rateLimit.remaining));
   ```

**Important:** If MongoDB is unavailable (connectToDatabase fails), the rate limit check should fail OPEN (allow the request) with a console.warn, NOT block all auth. Wrap the checkRateLimit call in try/catch with fallback to allow. This prevents a MongoDB outage from locking everyone out of login.

Do NOT modify `src/lib/rate-limiter.ts` -- the existing in-memory rate limiter stays for non-auth API routes (like finance). The MongoDB rate limiter is additive, not a replacement.
