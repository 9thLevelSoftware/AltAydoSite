Sweep ALL API route files under `src/app/api/` and sanitize error responses. The pattern to find and fix:

CURRENT (leaks internal details):
```typescript
catch (error: any) {
  console.error('Some context:', error);
  return NextResponse.json(
    { error: `Failed to do X: ${error.message}` },
    { status: 500 }
  );
}
```

FIXED (generic message, full logging preserved):
```typescript
catch (error) {
  console.error('Some context:', error);
  return NextResponse.json(
    { error: 'Failed to do X' },
    { status: 500 }
  );
}
```

Rules for the sweep:
1. **Remove `error.message` from ALL NextResponse.json() calls.** Replace interpolated strings like `Failed to create operation: ${error.message}` with just `Failed to create operation`.
2. **Remove `error.stack` from ALL NextResponse.json() calls** (only /api/diagnostic has this, which is being deleted in Plan 01, but check for others).
3. **PRESERVE the console.error() calls** -- those log server-side and are needed for debugging. Do NOT remove or change them.
4. **Keep the operation context** in the generic message. `{ error: 'Failed to create operation' }` is fine -- it tells the client WHAT failed without revealing WHY (MongoDB timeout, invalid field, etc.).
5. **Do NOT change 400-level responses** that return validation errors from Zod schemas -- those are intentional and safe (they describe what the client did wrong, not internal details).
6. **Do NOT change responses that use hardcoded strings** like `{ error: 'Unauthorized' }` or `{ error: 'Not found' }` -- those are already safe.
7. **Special case: `src/app/api/auth/signup/route.ts`** -- has `Database error: ${createError.message}`. Change to just `Database error` or `Failed to create account`.

Also fix any `error: any` type annotations to just `error` (untyped catch clause) or `error: unknown` per TypeScript best practices. The `any` type annotation on catch is a code smell but not a blocker -- fix it if you encounter it but don't go hunting for it specifically.

NOTE: Files being deleted in Plan 01 (diagnostic, force-fallback) or modified in Plan 01 (storage-status, cron routes, assign-synced-role, finance) may also have error.message. Plan 01 handles those files. If there's overlap (e.g., cron routes also have error.message), coordinate: Plan 01 fixes the auth pattern, this plan fixes any remaining error.message leaks. If a file is fully handled by Plan 01 (deleted or already sanitized there), skip it here.

Expected scope: ~35 files with ~80 instances to sanitize.
